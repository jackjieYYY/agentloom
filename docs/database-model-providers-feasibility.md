# 数据库模型配置与多 Provider 可行性报告

本文记录实施前的可行性分析与方案取舍；用户随后批准实施。当前使用方式以 [模型配置与 API 使用说明](model-configuration.md) 为准，Agent 组装方式以 [LangChain 接入约定](langchain-integration.md) 为准；下面的代码位置与工期属于分析时快照。

## 1. 结论

**可行，建议实施。** 现有 Agent 工厂已经接收 LangChain 的 `BaseChatModel`，数据库也已有 PostgreSQL、Drizzle 与迁移入口。无需更换 Agent SDK、重写执行引擎或引入模型网关。

建议将 provider 的连接配置、加密后的 API Key 和可用模型存入数据库；全局默认选择由前端维护。每次执行开始时读取配置，创建该次执行使用的模型实例，再交给现有 Agent 工厂。

首期建议采用：**全局配置、两张配置表、多个独立聊天、每次输入显式选择模型、一次执行固定配置、API 管理配置**。同一个聊天可以在消息之间切换模型，沿用该聊天已有历史。首先接入 OpenAI 与经过验证的 OpenAI 兼容服务；如果首期明确需要 Anthropic 或 Gemini 原生协议，再增加对应官方 LangChain 集成。

实现复杂度中等。配置读取和实例化比较直接，主要工作在密钥管理、聊天归属、会话恢复语义和 provider 协议验证。

## 2. 现状与依据

模型配置与加密凭证保存在 PostgreSQL，全局共享。执行层复用一个 Agent，在每次调用的 runtime context 中提供选定模型；聊天支持默认模型与单次覆盖，继续执行沿用最近执行模型。配置 API 提供创建、更新、启停、默认设置及 Key 轮换，允许修改路由信息；不导入旧配置或补绑旧 checkpoint。当前用法见 [模型配置文档](model-configuration.md)。

## 3. Provider 与模型分别表达什么

建议区分三个概念：

- **协议类型**：由代码明确支持的有限集合，例如 `openai`、`openai-compatible`；需要原生接入时增加 `anthropic`、`google-genai`。
- **Provider 连接**：一组具体的服务地址与凭证，例如一个 OpenAI 账号、另一个兼容服务账号。相同协议可以配置多个连接。
- **模型配置**：某连接下可供会话使用的模型，例如一个 OpenAI 连接提供多个模型。

Provider 的显示名称不能直接决定调用哪个 SDK。数据库只能选择应用已支持的协议类型，不能存入模块路径、构造器名称或可执行代码。

“多个 provider”有两种技术范围，成本不同：

| 范围                          | 接入方式                                                   | 依赖变化                 | 关键限制                                          |
| ----------------------------- | ---------------------------------------------------------- | ------------------------ | ------------------------------------------------- |
| 多个 OpenAI / OpenAI 兼容服务 | 复用 `@langchain/openai`，传入各自的 Key、模型和 `baseURL` | 通常无需新增依赖         | 必须实测目标服务的协议、流式输出及工具调用        |
| 多种原生协议                  | 分别构造对应 LangChain 模型，统一返回 `BaseChatModel`      | 需增加实际使用的集成依赖 | 消息内容、工具 schema、流式事件和取消行为存在差异 |

当前只安装了 `@langchain/openai`。Anthropic 和 Gemini 原生支持属于可行扩展，尚未在本项目验证；不能据此承诺所有厂商开箱即用。

**已确认的 SDK 注意点：** 当前 `@langchain/openai@1.8.2` 的 `ChatOpenAI._useResponsesApi()` 会根据模型名和参数自动选择 Responses API。`useResponsesApi: false` 并不保证所有情况都走 Chat Completions。因此配置了兼容服务的 `baseURL` 后，还必须验证实际请求路径。若目标仅支持 Chat Completions，应选择该版本可公开使用、能固定该协议的入口；实现时验证导出与升级稳定性，不依赖内部私有路径。

## 4. 推荐数据模型

### 4.1 `model_providers`：连接与凭证

| 字段                       | 用途                                                                  |
| -------------------------- | --------------------------------------------------------------------- |
| `id`                       | 服务端生成的 UUID                                                     |
| `name`                     | 展示名称                                                              |
| `type`                     | 应用支持的协议类型                                                    |
| `base_url`                 | 官方协议可使用代码内的固定默认地址；兼容服务要求显式配置              |
| `api_key_encrypted`        | 服务端加密后的凭证封装，包含解密所需的随机 nonce、认证 tag 和格式版本 |
| `enabled`                  | 是否允许后续执行使用                                                  |
| `created_at`、`updated_at` | 基本维护时间                                                          |

首期只支持 API Key 认证。无需 Key 的本地服务、云平台专用身份、任意请求头等，按实际接入需求增加，不用通用 JSON 预建全部认证方式。

### 4.2 `model_configs`：可选模型

| 字段                       | 用途                     |
| -------------------------- | ------------------------ |
| `id`                       | 对外选择使用的 UUID      |
| `provider_id`              | 使用的连接               |
| `model_name`               | 用于展示和调用的模型标识 |
| `enabled`                  | 是否允许后续执行使用     |
| `created_at`、`updated_at` | 基本维护时间             |

一个连接对应多个模型，避免每个模型重复保存 Key。暂不增加温度、推理等级、任意模型参数 JSON；真正需要时再为具体参数定义校验规则。

配置关联与约束：

1. 模型通过 provider ID 关联全局 provider，不建立数据库外键；创建时校验 provider 存在，创建后不允许修改关联。
2. 模型 PATCH 仅接受 `modelName` 和 `enabled`，只更新提交的字段；后端不保存全局默认标记。
3. 模型与 provider 的启用状态在执行时检查，配置更新不联动其他字段。
4. API 不提供配置物理删除；使用 `enabled` 停用。
5. 不新增用户管理表，继续使用可信 JWT 中的身份。

### 4.3 实际执行模型与恢复

每个 conversation 就是一个独立 chat，保留独立的 `thread_id` 和历史。按可信用户过滤的分页列表支持多个聊天的切换。不同聊天可以并行执行，沿用现有“同一聊天最多一个活跃调用”的规则。

`conversations` 只保存一个可空模型引用，不建立数据库外键：

| 字段                             | 用途                                                                 |
| -------------------------------- | -------------------------------------------------------------------- |
| `last_execution_model_config_id` | 最近一次新输入实际使用的模型，恢复其未完成任务时沿用，重启后仍可读取 |

前端维护模型选择，每次新输入必须提供 `modelConfigId`；后端不保存聊天默认模型，不回退上一轮模型。未提供或模型 ID 非法返回 400，模型或 provider 不可用返回 404。

建议接口：

| 操作                               | 请求或行为                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------------- |
| `GET /conversations`               | 只列出所属用户的聊天，使用有上限的游标分页；游标按 `created_at` 与 `id` 稳定排序 |
| `POST /conversations`              | 空请求体或 `{}`，不接收模型参数                                                  |
| `POST /conversations/:id/input`    | `{ "text": "...", "modelConfigId": "..." }`，两个字段均必填                      |
| `POST /conversations/:id/continue` | 不接收新模型，恢复该次任务已经记录的实际模型                                     |

例如，同一聊天依次提交模型 A、B、A，每一轮都读取已有历史，并在完整 Agent 执行期间固定使用本轮模型；工具调用后的后续模型请求也使用该模型。

模型下拉框代表下一条新输入的选择；当前执行使用的模型应单独展示。服务端查询返回最近执行模型的 ID 和模型标识。

新建聊天的模型引用为空；新输入执行前必须保存实际模型引用，继续执行时沿用该引用。开发阶段不提供旧版本数据导入或未完成 checkpoint 的兼容恢复。

该引用只保存最近执行的恢复依据，不代表每条历史回答的模型审计。如果未来需要每条回答显示确切模型与 token 用量，再补充执行记录或验证 SDK 可持久化的消息元数据，本期不承诺这项能力。

### 4.4 切换模型时的历史兼容

切换后继续使用同一聊天的 checkpoint，由新模型读取已有聊天历史；不创建新聊天，也不重新提交或重放旧输入。跨 provider 切换意味着已有上下文可能发送给另一个服务，界面应明确展示服务商与模型。

LangChain 的统一消息格式降低了适配成本，但不能保证原生 provider 的所有私有消息字段都能互转。首期应以文本聊天、标准工具调用和工具结果作为兼容范围：

- 普通回合结束后可以选择另一模型提交下一条消息，保留语义历史。
- 有未完成工具工作或待审批任务时，沿用现有规则阻止新输入；`continue` 和未来审批恢复使用原实际模型。可更改下一条消息的偏好，但不把半途任务交给另一 provider。
- 已关闭的聊天不能继续输入；现有 `/cancel` 表示永久关闭聊天，界面不能把它标作普通“停止生成”。若要求停止后立即换模型，需要另行提供仅中止当前调用的停止接口，并定义未完成任务的处置规则，不能用现有关闭接口代替。
- 针对实际接入组合验证 A → B → A、标准工具历史以及文本内容块。确有需要时在发送给目标模型前做协议适配，不覆盖已保存的原始历史，也不简单删除工具调用来“修复”错误。
- 首期不承诺图片、厂商私有推理块或私有工具状态可以任意跨 provider 迁移。检测到不兼容历史时开流前明确拒绝；不能静默丢上下文。若兼容性只能在远端确认，沿用脱敏 SSE 错误，不宣称全部问题都可本地预检。
- 不同模型的上下文窗口不同，切换可能超出目标上限；保持现有不自动摘要的规则，不静默裁剪历史。需要时明确报错，再独立设计受预算限制的上下文管理。

## 5. 配置更新与执行流程

推荐流程：

```text
校验 JWT 与会话归属
  → 检查会话关闭、活跃、审批和未完成任务状态
  → 新输入使用前端必填的模型 ID；继续使用已记录的实际模型
  → 读取全局已启用的模型和 provider
  → 解密凭证，创建本次模型实例
  → 新输入在 SDK 执行前持久化实际模型引用，写入失败则不执行
  → 再检查服务关闭状态，登记活跃调用
  → 创建新 Agent，沿用现有 SSE、调用限额和取消流程
```

用一个小的模型构造函数，根据明确的 `type` 分支返回 `BaseChatModel` 即可；不需要注册中心、插件加载器或新的 provider 框架。

每次执行只解析一次配置，并以读取到的配置固定整个调用。执行期间更新数据库，不修改已经开始的模型或工具循环；下一次执行重新读取，Key 轮换无需重启。首期不缓存配置，避免缓存失效问题。

最近执行模型必须持久化，不能只保存在进程内；否则重启后无法确定未完成任务应使用的模型。沿用会话短锁与单进程准入，在确认没有未完成任务后才能用新输入覆盖此字段。该写入不与 SDK checkpoint 原子提交，因此仅代表执行选择，不代表输入已保存或执行已完成；查询仍以 SDK 快照判断能否继续。

最近执行模型引用固定配置 ID，不固定路由快照。API 允许修改模型标识、provider 的协议类型和目标地址；模型与 provider 的关联在创建后固定。在途调用不变，显式继续使用该 ID 最新的配置，包括更新后的路由与凭证。停用配置会阻止新输入和继续。不提供不可变配置版本层。

查询当前使用 `reader.graph.getState()`，其 `reader` 来自启动时构建的 Agent。改造后必须保留**无有效 provider 时仍可查询和取消**：读取图只需具备相同图结构，不应依赖当前的可用 Key。可先保留仅供读取的图实例及显式占位模型，严格限制为 `getState()` 路径，并用测试保证不会执行模型；无需重写 SDK 状态读取。

## 6. 密钥、权限与地址安全

**数据库保存加密凭证，部署环境保留解密主密钥。** 使用 `jose` 的 Compact JWE，固定 `dir` 与 `A256GCM`，使用独立的 `MODEL_CREDENTIALS_KEY`，不复用 `AUTH_JWT_SECRET`。由库生成随机 IV、处理认证标签和序列化；provider ID 放入受认证的 protected header，解密时校验绑定，并限制允许的算法。

业务配置迁入数据库，不等于服务端可以完全没有环境配置。`DATABASE_URL`、JWT 密钥、凭证加密主密钥仍属于部署基础配置。数据库备份与主密钥应分开保管；主密钥丢失后，必须重新录入上游凭证。

首期主密钥由运维固定管理，更换时需要显式解密并重新加密既有凭证；不把简单换环境变量描述成完整的主密钥轮换方案。

安全边界：

- 查询接口只返回白名单元数据，不返回明文或密文；不用 `select *` 后再临时删除字段。
- API Key 不进入 Agent context、消息、checkpoint、SSE 或日志；配置和加解密错误继续脱敏。
- 浏览器只提交模型配置 ID，不能在会话输入中提交 Key、目标地址或任意 provider 参数。
- 配置全局共享；不存在的资源返回 404，聊天访问仍校验用户归属。
- 配置 `base_url` 会决定会话内容与 Key 被发送到哪里。通过 API 全局管理，校验协议并拒绝 URL 中的账号密码，使用 HTTPS。URL 字符串校验不构成完整的 SSRF 防护。

接口沿用 JWT 认证，使用 `sub` 标识用户。当前不区分管理员角色，所有通过认证的用户均可管理共享配置。

## 8. 初始化与验收

建议实施顺序：

1. 明确首批实际使用的协议与配置管理者；采用全局配置和 API 管理，暂不区分管理权限。
2. 新增数据库表、最近执行模型引用、约束及加解密功能。
3. 提供 provider 与模型配置读写 API；业务结构只维护在 Drizzle schema，由 pushSchema 初始化，不携带真实 Key。
4. 修改执行层、聊天列表与输入接口，接入选定 provider；保留不依赖真实 Key 的模型注入测试。
5. 更新部署说明，模型业务配置只从数据库读取。

验收至少覆盖：

- 多个 provider 和模型全局共享，不同用户均能查询、更新及执行；聊天按用户隔离。
- 同一用户的多个聊天拥有独立历史，列表只返回本人所属数据；分页稳定且有数量上限。
- 同一聊天可 A → B → A；每次新输入必须携带模型 ID，未携带时拒绝执行，不沿用上一轮模型。
- 临时选择 B 后发生中断或重启，继续沿用 B 的配置 ID，并读取该配置最新的路由、模型标识与凭证；待审批和未完成任务不能借切换模型绕过。
- 无配置、配置禁用或主密钥不可用时，在开流前拒绝执行；仍能查询、取消和启动服务。新增主密钥不能无条件成为健康检查和只读服务的启动前提。
- Key 轮换在下一次执行生效，在途调用保持原配置；并发输入或前端切换模型不会覆盖当前任务的实际模型记录。
- 跨 provider 的文本、工具消息与内容块经过兼容测试；超长或不兼容历史不静默裁剪。
- 流式文本、工具调用、取消、断线停止、超时、调用限额和显式继续保留既有语义。
- SDK 和底层客户端均不自动重试；429 不产生隐式额外请求；不自动故障切换到其他 provider。
- 加密 round-trip、密文篡改或跨 provider 替换失败，以及响应和日志不泄露 Key。
- 当前结构可在空库初始化及重复执行，已有 checkpoint 保留。
- 每个实际启用的协议进行小规模真实联调，覆盖工具调用与中断后的继续；接通普通聊天不作为 Agent 兼容性验收。

当前 SSE 和查询只接受字符串型文本内容。接入返回内容块的原生 provider 时，还需验证并按白名单提取可展示的文本，避免空输出；不能直接转发完整内容块中的思考、工具参数或其他内部信息。

## 9. 工作量与取舍

在维持当前单进程架构、配置 API 管理、不做前端的前提下，经验估计：

| 范围                                   | 估计         |
| -------------------------------------- | ------------ |
| 表结构、密钥处理、配置维护与初始化     | 1–2 个开发日 |
| 执行接入、聊天列表、模型切换与恢复校验 | 2–3 个开发日 |
| 回归测试、首批服务联调与文档           | 1–2 个开发日 |

合计约 **4–7 个开发日**，属于范围估计，并非已经验证的工期承诺。新增原生协议、自助管理权限和前端页面需另计；provider 的实际兼容性问题可能增加联调时间。

本期跳过自动路由、故障切换、负载均衡、Key 池、计费系统、模型自动发现、配置缓存和管理前端。数据库模型配置本身不需要这些能力，尤其自动切换 provider 会改变恢复语义与会话数据流向。
